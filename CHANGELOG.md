### Added

- Cover every public CLI command with a runnable journey, and make an uncovered command fail the suite. The dogfood that produced the previous entries found a universal install failure no test could have caught: nothing exercised a real GitHub source archive through the actual argument parser and production composition, so every command's "coverage" was a mix of service-level tests and empty-project smoke runs that pass whether or not the command does anything. `cmd/acr` now carries one journey table. Each entry runs real argv through the shipped `runWith` composition against a stateful GitHub fixture — releases, commits, tarball and asset redirects, uploads and readback — reached through the production `GitHubClient` at its production hostnames, so the client keeps building, authenticating, redirect-checking and origin-validating exactly the requests it builds against GitHub. Source tarballs carry the leading `pax_global_header` and the group permissions codeload actually serves, so the two failures the dogfood found stay covered by shape rather than by anecdote. `TestCLIJourneyInventory` then holds the completed journeys against `cli.Leaves()`: every one of the 15 executable leaves needs a successful outcome and a refusal, and a journey registers coverage only after asserting a positive result, so a help-only or empty-state test satisfies nothing. The inventory enumerates the dispatch registry `commandFor` accepts rather than the display order, because a first attempt derived it from `commandOrder` and a command added to `commandSpecs` alone was then dispatchable, undocumented and uncovered all at once — the gate now runs against the production surface with exactly that command added and has to name it, alongside `TestCLIJourneyInventoryFailsForTheIntendedCause`, which mutates a synthetic inventory the same ways — a new command, a new subcommand, a removed journey, a leaf that only refuses — and requires a complaint by name for each. Where a journey reasons about elapsed time it holds the clock still: `freshnessapp.NewApplication` takes an optional clock that `publishapp`, `migrateapp` and `runWith` forward untouched, so the throttle journey crosses Window-1s and Window on purpose instead of passing because the suite is fast, and without an option the composition is byte-for-byte the one the binary ships. The publish journey is the whole arc: a real tagged Git repository is published through the boundary and a consumer that has never seen it installs, realizes and checks the release that publishing created, with no post-publication state seeded by hand. Three lanes are recorded separately because they establish different things: the composed in-process stack, a composed subprocess with real descriptors and exit statuses, and the compiled shipped binary for local and offline behavior. What none of them establish — live GitHub conformance, real agent loading, fixture provenance capture — is written down in [`docs/testing.md`](docs/testing.md) rather than implied to be covered, and the two checks that would establish the first two are runnable procedures rather than intentions: [`docs/manual-conformance.md`](docs/manual-conformance.md) carries the read-only binary lifecycle check and the per-agent canary, each with its isolation, the identities to record, the nonempty observations a pass requires and a pass/fail/blocked classification, on a monthly plus contract-change cadence. The canary needed a fixture rather than a paragraph: the first draft sent the operator to the lifecycle check's own scratch consumer, which that check uninstalls twice and then deletes and which only ever selected two of the three adapters, so following the stated order left nothing installed to observe. The canary now has its own consumer and its own local package — [`docs/canary-package/`](docs/canary-package) carries an always-on rule, a rule scoped to `docs/**`, a discoverable skill and a session-start hook that appends one marker line to a scratch log and does nothing else, vendored through `acr migrate tessl` so no publication and no network are involved. The phases are numbered with the observations before the teardown, each observation names how it is captured and what makes it a failure, and `cmd/acr/canary_test.go` executes every phase except starting the agents, so what stays manual is the observation rather than the setup. The first version of those observations could still pass without the thing they describe ever happening: every agent read one shared marker log, so a runtime whose hook never ran inherited the first runtime's line, and a rule row was satisfied by an agent that searched the fixture and quoted the sentinel back. Each agent now gets its own absolute `ACR_CANARY_LOG`, proven absent before the session and holding a new marker after it, with a reset-and-increment form for runtimes that cannot pass an environment variable through to a hook — a marker that was already there, another agent's line, a registration, or a hook run by hand never counts. That fallback could not run at all on the consumer it was written for: it copied and truncated a log that only exists once a hook has appended to it, so on a freshly prepared consumer both the copy and the truncation failed on the missing `.acr-canary/` parent and the first observation had nowhere to start. It now creates the parent, archives a prior log only when there is one and records the absence when there is not, and initializes the log itself; the steps are chained so an archive that fails stops the sequence rather than truncating evidence it could not preserve. It also says where the agent has to be started, because with `ACR_CANARY_LOG` unset the hook writes to a relative path that resolves against whatever working directory the runtime hands it. The rule rows require clean sessions and tool-free first turns, prompts that name neither a sentinel value nor a fixture path, and whatever tool or attachment trace the runtime already provides; an answer that came from a file search is invalid rather than a pass, and a runtime that cannot show the difference is blocked rather than passing. Skill discovery is established from a native listing before the skill is invoked, and the scoped-rule row belongs to Cursor alone, because ACR's Cursor adapter is the only one that realizes path scoping into its own `.mdc` while its Claude Code and Codex adapters render the same rule into the always-on host, which makes the row a statement about what ACR wrote rather than about what those runtimes can do. [`cmd/acr/fixture-provenance.md`](cmd/acr/fixture-provenance.md) sits beside the builders and separates what was observed from a real GitHub tarball — endpoint, observation date, capture digest, PAX header, root, mode sets, ordered entries — from the response bodies written from the API contract, names the capture fields nobody kept, distinguishes the capture digest from the published asset digest and the canonical content hash, and states the same refresh cadence and its reviewed structural diff. Three of the tests the review round then read were asserting spelling rather than outcome, and each had a way to be wrong in both directions. The composed clock's default was checked by `reflect.Pointer` identity against `time.Now`, so wrapping the default in a closure that reads the same source broke a test nothing observable had changed; it is now held to what a live clock does — a non-zero reading that never runs backwards — which a wrapper leaves passing while a default that stopped reading a real clock still fails. The canary hook's isolation rested on a word-boundary regexp over program names plus a substring search for `$HOME` and `http://`, which a comment mentioning `curl` fails and a program reached through a variable passes; the hook now runs in a sandbox with every program it would need shadowed on `PATH` by a recording stub, a home of its own and a log path carrying a space, so an external call, a write outside the log and a split path each fail by name, and a second test covers the log it cannot write — a stderr diagnostic naming the marker, nothing created, and an exit that leaves the agent session running. The hook itself gained the entry-point guard that makes importing it possible without recording a dispatch that never happened, and the compiled binary the three meta lanes share gained a `TestMain` that removes its build directory once every consumer has finished, which no per-test cleanup could do and which a failed build previously leaked outright. The canary skill also picks up the execution-mode preamble and the flat numbered step every skill it stands in for carries, and the rationale sentences on the always-on rule and the skill move here, off a surface that is loaded into every session. The credential-order fakes were passing over a failure of their own: the scratch `PATH` holds nothing but the fakes, so the `cat` the git fake used to consume the credential request was not there, and without strict mode the fake carried on past the missing command and printed the password anyway — the order was proven while the request was never read. Each fake now runs bash at a resolved absolute path under `set -euo pipefail`, consumes the request with shell builtins, and answers only a request that names the host, so dropping the host from what discovery sends fails the case.
- Answer `acr init` over a real pseudo-terminal in the journeys. The interactive path was previously proven only by the probe that decides it and by the refusals every non-terminal shape takes; a typed selection now travels through an actual terminal into `agents.yaml`, and an unparsable answer re-prompts instead of choosing something nobody asked for.
- Prove the credential discovery order end to end. `GH_TOKEN` before `GITHUB_TOKEN` before `gh auth token` before `git credential fill` was only ever exercised by injecting a token provider, which proves nothing about the order the commands are tried in or about the `GIT_TERMINAL_PROMPT=0` that keeps a helper from blocking. The order is now driven through real executables on a scratch `PATH`.

### Changed

- Take the credential-discovery deadline as an argument. `go test -race ./...` failed in `TestDiscoverGitHubTokenPrefersEnvironmentThenCommands/git_credential_fill_is_the_last_resort`, which returned no token where it wanted `from-git`; the subtest took 10.07 seconds against 0.52 in a focused run, and the only timer in that path is `commandToken`'s five-second per-command deadline. Two of them is exactly 10 seconds, an abandoned command is the only way that fake can produce an empty token, and the fake's other two failure modes — a request naming no host, and prompting left enabled — are load-independent and would fail the focused run too. The test was asserting the order the sources are tried in, and racing a wall clock to do it. `discoverGitHubTokenWithin` now takes the budget, `discoverGitHubToken` supplies the five seconds the binary has always used, and the order test passes zero so the assertion has no clock in it at all. The budget keeps its own test, written the only way a budget test survives a loaded machine: a helper that never answers is abandoned, which a slower machine only overshoots further, where a helper that must finish inside a budget is the coupling being removed.
- Bump the `claude-code`, `codex` and `cursor` adapters to `1.0.1`. Their skill output changed with the reference-rebasing fix above, and [`docs/adapters.md`](docs/adapters.md) makes an adapter's own output change a `Descriptor.Version` bump rather than a boundary bump; the adapter/coordinator API those implementations are compiled against is unchanged, so the boundary stays `1`. The recorded `adapterVersion` in every ledger entry follows, which is metadata nothing compares — a consumer realized against `1.0.0` re-realizes without a drift refusal.
- Make the executable command surface enumerable. The accepted subcommands of `freshness` and `migrate` were literals inside parser branches, so nothing outside the parser could list what a user is able to run, and the meta commands were a hard-coded switch plus two hard-coded help lines. Both are descriptors now, `cli.Leaves()` returns the 15 executable leaves the parser dispatches on and help renders, and the acceptance suite enforces coverage against that rather than against a hand-maintained list or a Go AST reader that any internal refactor would break. `NewGitHubClient` takes options so a test can supply an HTTP client while keeping the production API host, upload host and trusted redirect origins; without options it is the client the binary already shipped.
- Make the fake GitHub remote observable, closing issue #67. `PublishRelease` mutated a range-loop copy, so a published release stayed a draft in every stored representation; `DeleteRelease` logged the identifier and left the release visible to later lookups; `UploadAsset` never associated the asset with its release. A publisher-to-consumer journey through that double could only pass by seeding the outcome it was meant to prove. The live release index is now what every lookup reads and every publication method mutates, the creation and deletion slices are the event logs they were named for, and reads hand out copies so a caller editing a returned asset slice cannot corrupt storage. Repairing the mutations was not enough on its own: the `Latest` and `Releases` seeds still answered before the live index, so a release deleted through the publication API kept answering the consumer views seeded with it and a release published through the double stayed hidden behind an older `Latest` seed — one `Remote` could call the same release absent for a publisher and present for a consumer. Every lookup now resolves live index first, seed second and tombstone never; a publication advances what `LatestRelease` returns; a seeded release can be uploaded to and published, which promotes it into the live index; and the seeds a caller wrote stay where they were put. Unifying the views moved the remaining defect into identifier allocation, because latest selection and deletion then keyed on identifiers the counters handed out from fixed floors regardless of what a caller had seeded: a seeded release at 1001 collided with the next generated one, so deleting the new release tombstoned the seeded one; a seed at 5000 hid every later publication behind it; and an upload reused a seeded asset id, rewriting the bytes of an asset nobody uploaded to. Allocation now advances past the highest identifier visible anywhere — the live index, every seed, the assets those releases carry, the creation log and the tombstones, so a deleted identifier stays reserved — and no caller adjusts a counter and no fixture lowers an id to make a test pass.
- Stop hashing Git's own storage in documented-command snapshots, closing issue #76. Background maintenance wrote `.git/objects/maintenance.lock` while a documented command ran, and the before/after comparison failed for a reason the command under test had nothing to do with. The shared snapshot skips Git internals and records what the promises are made of instead — permission bits, symlink targets and directories alongside content digests — plus `.git/info/exclude`, which ACR owns a generated block in. Excluding the storage also hid the index and the refs, so a command could stage a mode change or move HEAD and every composed journey would still call the project unchanged; the snapshot now records what Git answers rather than what Git stores — the commit HEAD names, the branch, every index entry with its mode and blob, the working-tree status, and the exclude file resolved through Git so a linked worktree's common-directory copy is covered too. The probe stages a mode change and moves HEAD without touching a product byte, and both have to fail the snapshot while maintenance lock churn still must not.
- Supply the repository metadata stage 0 of the migration guide actually needs, for issues #83 and #84. Following the stage verbatim on a real Tessl plugin, the first prescribed `acr migrate tessl-plugin --dry-run` refused at `required`, because real manifests have no `repository` field and the guide never said to supply one. The stage now names the prerequisite up front and demonstrates `--repository` on both the rehearsal and the apply. It also told the operator to review the proposed `agent-plugin.yaml` before applying, which neither the text nor the JSON dry run emits — those bytes exist only once the conversion has run for real — so the review moved to where the file exists rather than growing a preview flag the tool does not need. The `producer` documentation fixture drops its repository field so the executable harness runs the walkthrough against the shape the guide claims to describe.

### Fixed

- Rebase a reference only when the package can prove it owns the tree, for issue #92. The first fix accepted any two path segments after `.tessl/plugins/`, so a package declaring `skills/advocate` rewrote another package's `.tessl/plugins/other/plugin/skills/advocate/scripts/check.sh` into its own directory: an independent probe extracted that command from realized content and it ran this package's helper instead of the one it named, on all three adapters. The identity is the only evidence separating "my own installed tree, before ACR owned it" from "somebody else's tree that happens to expose the same skill path", and it cannot be recovered from the ACR name — `source.repository` binds that name to the GitHub repository, so a package republished under a different repository name loses it entirely. Migration is where the identity is still known, so migration records it: `acr migrate tessl-plugin` writes the Tessl plugin name it converted into the new optional `source.tesslIdentity`, `acr migrate tessl --vendor-unmapped` writes the `<workspace>/<package>` the tree was installed under, and the adapter rebases a legacy reference only for a recorded identity or the package's own name. A package published before the field existed keeps its package-root references working and preserves its legacy ones rather than guessing; [`docs/migration-producer.md`](docs/migration-producer.md) carries the convert-and-republish path that restores them, which is what the FFA dogfood package needs — its 27 legacy references carry the `jbaruch/frequent-flyer-advocate` identity its files were written against while the published copy is named `jbaruch/ffa-acr-dogfood`, and nothing in those bytes says the two are the same package. Consumers reject an unknown manifest key, so the CLI release ships before any package carrying the field.
- Recognize a reference as a whole token rather than by the byte in front of it, for issue #92. Deciding on one preceding byte rewrote a URL query value (`https://example.test/?next=skills/...`), a filename with a punctuation or non-ASCII prefix (`archive#skills/...`, `caféskills/...`), and — through an identity reader that took the next two slashes whatever lay between them — a purported workspace containing whitespace, prose spanning two lines, and the closing quote, newline and opening quote between two adjacent Python literals in the published FFA package's own `tests/test_trackers.py`. The previous round's report claimed those literals were untouched; source-versus-materialized comparison disproved it. Content is now cut into tokens at the bytes a supported reference cannot contain — whitespace, the three quote characters, and the bracketing pairs — and a token qualifies only when a supported form starts at its beginning, after at most one leading escape and one shell assignment prefix (`NAME=` or `--flag=`), which is what keeps `--file=skills/...` working while a URL query keeps its bytes. Each of those inputs is now a token that does not begin with a supported form, so each is preserved without an alphabet of exceptions to maintain.
- Resolve the bundled helper a rule requires, for issue #92. Rebasing reached skill files only, so all three realized FFA rule hosts still named `skills/frequent-flyer-advocate/scripts/letter-fit.py`, which does not exist from the consumer directory — and that rule requires the script to measure a letter and forbids any other count, so the unresolved path was operational rather than prose. A rule body now resolves against the installed tree of the adapter that owns its instruction host: `.claude/skills` for a Claude-owned host, `.codex/skills` for a Codex-owned one, `.cursor/skills` for Cursor's own `.mdc`. When Claude and Codex share one host, every client reading it reaches the owner's tree by the same project-relative path, so the single contribution stays reachable to both and the rule body is still written once. The regression realizes Claude-only, Codex-only, Cursor, two separate hosts and one host reached through an import, and executes the command it extracts from each.
- Preserve a foreign include added to a generated-only instruction host, closing issue #93. Tessl adding `@AGENTS.md` plus its own prose to an ACR-created CLAUDE.md moves the rule contribution to AGENTS.md and omits CLAUDE.md; the compiler revisited an omitted target only when its prior ownership was shared, so the previously generated-only host fell to the engine's plain delete path and every later `check` and `realize` exited 4 with `CLAUDE.md: refusing to remove modified managed output`. The managed block was intact and only foreign bytes had been added. An omitted target whose ledger entries are homogeneously managed blocks is now revisited whichever ownership it held, which produces the hash-bound preservation proof the planner already accepted for the shared case: the foreign bytes survive, ownership drops to unmanaged, the contribution lands once on the new host, and re-realizing is a no-op. A plain generated file is deliberately still excluded — the engine owns its whole content and its removal path was already right — and an omitted host whose managed block was actually edited still refuses.
- Rebase a skill reference as a whole path for issue #92, so the commands a realized skill instructs an agent to run actually resolve. The first persistent FFA adoption through Homebrew ACR 0.1.3 installed cleanly, `acr check` reported current, and every helper command in the realized skills pointed at a file that does not exist: rebasing replaced the package-relative substring anywhere it appeared, so a legacy Tessl-installed path became `.tessl/plugins/jbaruch/frequent-flyer-advocate/.claude/skills/acr__jbaruch__ffa-acr-dogfood__frequent-flyer-advocate/scripts/letter-fit.py` — a native directory spliced into the middle of the path it was supposed to replace. The rewriting was self-consistent, which is why nothing caught it; the package's own tests asserted the mount path its source shipped with, and ACR's tests asserted the rule rather than the outcome. A reference is now rewritten only where it starts a path, so an interior segment, a URL and another package's tree keep their bytes, and the two forms ACR does support — the package-root path and `.tessl/plugins/<workspace>/<package>/` followed by that same path — are each replaced whole. The Tessl identity is matched structurally rather than against the package source, because the dogfood package was republished as `jbaruch/ffa-acr-dogfood` while its files still name the `jbaruch/frequent-flyer-advocate` identity they were written against, and no package-specific string would generalize. Rebasing also stopped at the skill it was rendering, so the router skill's commands, which invoke the advocate skill's tracker, were left addressing the Tessl tree; every renderer now applies its package's whole skill set, nested trees before the ancestors that contain them. The regression is the composition rather than the rule: a two-skill fixture is realized for all three adapters, every command its realized `SKILL.md` files instruct an agent to run is executed from the project directory with the argument it carries, and its unsupported references are held byte-for-byte alongside a companion file that must not change at all. What stays outside the contract is written down in [`docs/adapters.md`](docs/adapters.md) rather than guessed at: a reference ACR cannot map is preserved rather than rewritten into a path that resolves nowhere, and rule bodies are not rebased at all because they render into the shared instruction block, which owns no installed tree.
- Name the outputs an unapplied change would write. `acr check` exited `3` reporting only how many changes were pending, which told the reader a number and gave no way to find out which files it meant; the refusal now names the affected paths, bounded at five so a badly drifted project still produces a diagnostic worth reading to the end. A ledger-only change has no path and keeps the count-only form. A drift that is both files and ledger names the ledger after the paths, so the count and the list it introduces describe the same set.

- Accept GitHub's PAX metadata in source archives for issue #79, so `acr install github:OWNER/REPO` works against real GitHub for the first time. Every repository tarball GitHub serves begins with a global PAX header entry named `pax_global_header` carrying the commit id; root detection counted it as a second package root and refused the archive before reading any package content, and no producer could work around a record GitHub adds. PAX metadata entries are now skipped during enumeration while still counting against the entry bound, so resource accounting is unchanged and the link, duplicate, traversal, and special-file guards are untouched. The regression fixture for issue #80 builds the real GitHub shape programmatically — global header, per-file extended header, both, and neither — rather than committing a binary archive; a metadata-only archive still refuses as empty. Found minutes after 0.1.1 shipped by the first end-to-end dogfood, which copied a real Tessl plugin, converted it, published `github:jbaruch/ffa-acr-dogfood@v0.9.38`, and could not install it.
- Normalize extracted package file modes to the 0644 / 0755 pair every publisher records. With the PAX refusal gone, the first real install reached the next universal blocker: `release metadata content hash mismatch`. GitHub serves source tarballs with group-write permissions (0664 and 0775) that no publisher writes, and `internal/tarball`, `internal/publish`, and the vendor file records all reduce a mode to the executable-or-not pair, so a content hash computed from a source tree could never equal the hash in the release metadata. Extraction now applies the same rule: the recorded FFA source archive hashes to the published `sha256:91328738a779e5fe4c330b1f3dac8ef6a3af7091642caa8f981b8c1e6d7f1208`, and realization no longer carries a group-write bit into native output. Found by rerunning the dogfood install against the fixed binary; it has no issue of its own because nothing had ever read a real GitHub archive far enough to see it.
- Name the roots a multi-root refusal actually saw for issue #81. The refusal read `publish one package root`, a remedy that cannot help: a genuine second root is a property of the downloaded archive, and the producer may already publish exactly one. It now names both roots and points at the archive and the source it was built from.
- Match each `acr init` answer hint to what its question accepts for issue #82. The hint chose its wording from whether a default existed rather than from how many options an answer may name, so the agent question accepted a comma-separated list while advertising one answer, and the freshness question accepted one policy while advertising several. Both real answers worked, so the prompt was wrong in two directions at once. Arity now comes from the question's kind and the Enter shortcut from its defaults, which are independent properties.
- Say when `acr outdated` has nothing to check for issue #85. A project with no declarations reported `All latest dependencies are current.`, which is vacuously true and reads as a positive result — in the dogfood it appeared immediately after a failed install, where it looked like confirmation the install had worked. The renderer now distinguishes an empty project, an all-pinned or vendored one, and a genuinely checked-and-current one. `Service.Outdated` keeps its signature and the JSON stays `{"outdated": [...]}`, so the session-start checker is untouched.
- Transition a final shared-Markdown removal to unmanaged ownership for issue #55. Removing the last ACR-managed block produced a candidate that still claimed shared ownership, which the realization planner refuses, so uninstall failed on `AGENTS.md` and `CLAUDE.md` with `final shared-target removal must transition to unmanaged ownership` and the lifecycle stopped at a successful install. ## 0.1.0 — 2026-09-04

### Added

- Document the complete MVP adoption journey for issue #3: executable offline command examples, per-command safety and rollback contracts, shared-file preservation goldens, structured troubleshooting, supported-adapter parity, Tessl consumer migration and producer dual-publishing guidance, plus command/code/link drift checks.
- Add `acr uninstall SOURCE [--dry-run]` and the interactive setup flow for issue #13. Uninstall is a state prune plus the ordinary realization pass, never a second removal engine: it drops the declaration, its rollback hold, and its lock row, then re-renders the pruned state so the planner deletes a generated-only target the remaining packages no longer want and splices a shared one down to its other owners, both bound to the observed hash. Removal keys on the declaration rather than on a ledger `Entry.Source` match, because `freshness.HookPackage` contributes the session-start hook under this repository's own source and a source match would delete the hook of any project that also declares it. It accepts no `--agent` and realizes across the union of the declared agents and every agent the ledger records, so a narrowed selection cannot leave another agent's outputs carrying entries for a package that is gone. A remaining package that cannot be materialized exits `1` with `remaining_packages_unavailable` before any file is planned; only the last dependency uninstalls fully offline, which a package cache would fix outside this issue. Setup adds `acr init` and the first-install questions in one outermost `internal/setupapp` decorator that holds the only `Prompter`, so `internal/dependency` gains no prompt-aware code, no `io.Reader`, and no new flag; the stored selection is what `init` pre-selects on a configured project and detection only contributes candidates, absence of `agents.yaml` rather than an empty `agents` list triggers the first-install questions, an empty selection is refused as `no_agent_selected` in every mode, and a rollback install asks the three-option `--hold`/`--pin`/cancel question whose first attempt is free because the install service refuses before it resolves anything. `--json`, `--non-interactive`, a non-terminal stdin, and a closed stdin all skip every question and take the typed refusal; the one terminal probe lives in `cmd/acr` and is true only for a real terminal, because a character-device test alone is not that test. The Go runtime opens `/dev/null` into a closed descriptor 0 before `main` and `/dev/null` carries `os.ModeCharDevice`, so a character-device probe reads a process started with stdin closed as a terminal and asks a question nobody can answer. The probe issues the stdlib termios ioctl per OS — `syscall.TIOCGETA` on darwin, `syscall.TCGETS` on linux, non-interactive on every platform without one — behind an `os.SameFile` comparison against `/dev/null`, and every error along the way reports non-interactive rather than fatal. End of input cancels a question before its line is parsed, so a preselected agent set or the preselected `outdated` never stands in for an answer nobody gave and a partial line without its newline is not a submitted one; a declined init question exits `2` with `setup_cancelled` having written nothing, and `acr init --non-interactive` on a configured project returns the stored selection before detection runs, so a malformed detected agent file cannot fail an invocation with nothing to decide. After `agents.yaml` and `.agents/registry.lock`, uninstall's previous-ledger path invariant names `.git/info/exclude` as its sole non-state exception: the `# BEGIN ACR GENERATED OUTPUTS` block is ACR's own local metadata rather than a package output, so removing a generated-only target also prunes that target's pattern from the block, while the file itself and every byte outside the block stay untouched.
- Add `acr migrate tessl` coexistence migration for issue #2: explicit manifest/file/CLI package mappings, Tessl-version-to-release-tag resolution, effective rule/skill/hook comparison, ownership and finalization-readiness reporting, ACR-only realization that byte-freezes Tessl state, duplicate-effect and gitignored-state diagnostics, and a parsed non-writing `--finalize` handoff for issue #8. Realization now uses a schema-versioned, fsynced before-image journal and non-blocking project claim so native output, `agents.yaml`, and `.agents/registry.lock` recover together before replanning after interruption, and `tessl_owned_target` refuses an ACR plan aimed at Tessl-owned bytes at exit `4`. A verified content cache that can eliminate immutable archive downloads on converged reruns is tracked in [issue #50](https://github.com/jbaruch/agentic-context-registry/issues/50).
